# Lontar

A fast, lightweight desktop database client for PostgreSQL, MySQL/MariaDB and
SQLite, built with Go + [Wails 3](https://v3.wails.io) and React/TypeScript.

Lontar are the palm-leaf manuscripts once used in Bali and Java to record knowledge.

*Formerly dbedit.* Lontar moves your existing connections, passwords and
history over on first start; see "Upgrading from dbedit".

## Prerequisites

All platforms:

- Go 1.26+
- Node.js 24+ and npm
- Wails 3 CLI: `go install github.com/wailsapp/wails/v3/cmd/wails3@v3.0.0`
- Docker (or Podman with the Docker API socket) — only for the database
  integration tests

Per OS:

| OS | Requirements |
|---|---|
| Linux | C toolchain + GTK4/WebKitGTK 6.0 dev packages. Debian/Ubuntu: `sudo apt install build-essential pkg-config libgtk-4-dev libwebkitgtk-6.0-dev`. (The legacy GTK3 stack, `libgtk-3-dev libwebkit2gtk-4.1-dev`, is used only when building with `-tags gtk3`.) |
| Windows | Microsoft Edge WebView2 runtime (preinstalled on Windows 10 21H2+/11; otherwise install the Evergreen runtime). |
| macOS | Xcode Command Line Tools: `xcode-select --install`. |

Run `wails3 doctor` to check your setup.

## Development

```sh
cd frontend && npm install && cd ..
wails3 dev            # hot-reloading app (Go + Vite)
```

Bindings for Go services live in `frontend/bindings/` and are generated — do
not edit them by hand. Regenerate after changing a bound service:

```sh
wails3 generate bindings -clean=true -ts -i
```

## Tests

Tasks are run with Wails' bundled task runner (`wails3 task <name>`; a
standalone `task` binary works too):

| Task | What it does |
|---|---|
| `wails3 task test` | Go + frontend + `tools/` tests |
| `wails3 task test:go` | `go test ./... -coverprofile=coverage.out`, including container integration tests (needs Docker) |
| `wails3 task test:go:short` | Go unit tests only (`-short`, no Docker) |
| `wails3 task test:fe` | `vitest run --coverage` (fails below 80%) |
| `wails3 task cover` | Prints Go coverage and fails if the total (excluding `main.go`) is below 80% |
| `wails3 task test:tools` | Tests the build helpers in `tools/` (a separate Go module; also part of `test`) |

SSH tests use an in-process SSH server (`internal/sshtest`) and never touch
`~/.ssh`. TLS tests start their own PostgreSQL and MySQL containers with
certificates generated by `internal/tlstest`. Cross-platform vet: `GOOS=windows
go vet ./...`, `GOOS=darwin go vet ./internal/...` and `GOOS=darwin go vet -tags
server ./...`. The root package's darwin GUI build needs cgo, so it can only be
vetted on macOS.

Integration tests use `internal/testutil`, which starts PostgreSQL 16, MySQL 8
and MariaDB 11 with testcontainers-go (once per package via `SharedPostgres(t)`
etc. plus `testutil.Main` in `TestMain`) and provides `SQLiteTemp(t)` for
SQLite. They skip automatically with `-short` or when Docker is unreachable.

With rootless Podman, start the API socket first and point `DOCKER_HOST` at it:

```sh
systemctl --user start podman.socket
export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/podman/podman.sock
```

The SQL splitter has a fuzz test. Normal runs use only its seed corpus; to fuzz
locally, run `go test -run XXX -fuzz FuzzSplit -fuzztime 60s ./internal/sqlsplit`.

Integration tests share a fixture, `testutil.SeedBrowse`. It holds every
value type, a view, tables with no or a composite primary key, and a table
and columns with awkward names. Run it against each engine (SQLite always;
PostgreSQL, MySQL and MariaDB when Docker is available). The structure tests
add `testutil.SeedStructure`: composite and self-referencing foreign keys, a
cross-schema key (PostgreSQL), partial, expression and GIN indexes, checks,
generated and identity columns, comments, triggers and views. On PostgreSQL,
the reconstructed DDL is executed in a fresh schema and must give the same
structure back. The sidebar object tests add `testutil.SeedObjects`: a
function (overloaded), procedure, aggregate, owned sequence, enum,
composite, domain and trigger on PostgreSQL; a function, procedure, trigger
and event on MySQL/MariaDB, plus a sequence on MariaDB; a trigger on SQLite.
Every object must be listed with its kind and detail and have a DDL, forged
references must be refused, and on PostgreSQL the DDL of every object is run
in a fresh schema and must list and print the same way.

## Browsing tables

After connecting, the sidebar lists the tables and views of the current
schema, then its other objects (see below). Switch databases (PostgreSQL, MySQL/MariaDB) or schemas
(PostgreSQL, attached SQLite databases) at the top. A single click previews
a table in a reusable tab, and a double click keeps it open. Rows load in
pages of 300. The status bar shows the server's row estimate until the
exact count is known.

| Shortcut | Action |
|---|---|
| Mod+R | Refresh the table and object lists and the current tab |
| Mod+F | Toggle the filter bar (Enter applies) |
| Mod+I / Space | Toggle the row detail panel |
| Mod+C | Copy the selected cells as TSV |
| Right-click | **Copy** (cells as TSV) and **Copy value** (the cell's full value, line breaks kept); works in read-only grids too |
| Mod+W | Close the tab |
| Mod+1 … Mod+9 | Switch tabs (Mod+9 = last) |

Click a column header to sort it (ascending, then descending, then off).
Shift-click adds a secondary sort. Filter values are always sent as bound
parameters. The filter bar's **Raw SQL** mode instead takes a WHERE
condition you type, and uses it verbatim against your database.

### Functions, sequences, types, triggers and events

Below **Tables** and **Views**, the sidebar lists the schema's other
objects in collapsible groups. A group is hidden when it is empty, shows its
count, and stays collapsed across restarts. The search box filters every
group (triggers also match by their table name).

| Group | PostgreSQL | MySQL | MariaDB | SQLite |
|---|---|---|---|---|
| **Functions** | functions and aggregates | stored functions | stored functions | — |
| **Procedures** | procedures | procedures | procedures | — |
| **Sequences** | sequences (with current value and owning column) | — | sequences (10.3+) | — |
| **Types** | enum, composite and domain types | — | — | — |
| **Triggers** | all triggers of the schema's tables | triggers | triggers | triggers |
| **Events** | — | scheduled events | scheduled events | — |

Materialized views stay in **Views**. On PostgreSQL, objects created by an
extension and the sequences behind identity columns are not listed.

Click an object to open it in a read-only **object tab**: its details (for
example arguments, return type, language and volatility of a function; the
range, increment and current value of a sequence; the values of an enum; the
timing and events of a trigger) and its DDL, with **Copy DDL** and **Open in
new query tab**. A trigger's table name opens that table. Mod+R reloads the
objects and the open object's DDL. Right-click an object for **Copy name**,
**Copy DDL** and **Open in new query tab**.

The DDL comes from `SHOW CREATE FUNCTION|PROCEDURE|TRIGGER|EVENT|SEQUENCE`
on MySQL/MariaDB and from `sqlite_master` on SQLite. On PostgreSQL,
functions and procedures use `pg_get_functiondef` and triggers
`pg_get_triggerdef`. Aggregates (without moving-aggregate and serialization
functions), sequences (with `OWNED BY`) and types are rebuilt from the
catalog. Comments are included. On MySQL/MariaDB a routine you may run but
not read (you are not its definer and lack `SHOW_ROUTINE`) shows a note
instead of its body. The object a tab shows is always looked up again in the
catalog before its DDL is read.

## SQL editor

**Mod+T** (or **New query**) opens an SQL tab next to the table tabs. Double-click
a tab to rename it. Each tab has its own database connection, kept from the first
run until the tab is closed. That means `BEGIN`/`COMMIT`, `SET`, `USE`,
`SET search_path` and temporary tables carry over from one run to the next. The
connection is also released when you disconnect or switch databases in the
sidebar, and after 30 minutes without a run. An open transaction is rolled back
whenever the connection is released. The toolbar shows **Transaction open**
while one is active. On MySQL, MariaDB and SQLite this is inferred from the
statements you run, so it is marked "(guess)".

| Shortcut | Action |
|---|---|
| Mod+Enter | Run the selection, or the statement under the cursor (highlighted) |
| Mod+Shift+Enter | Run the whole script |
| Mod+Shift+E | Explain the selection, or the statement under the cursor (query plan) |
| Mod+Shift+F | Format the selection, or the whole script (in the editor) |
| Mod+Shift+O | Open a `.sql` file |
| Mod+Shift+S | Save the tab to its `.sql` file (Save as for a new tab) |
| Esc | Stop the running query |
| Mod+F | Search in the editor (in a table tab it opens the filter bar) |
| Ctrl+Space / typing | Autocomplete tables, columns, `alias.column` and keywords (see below) |

Autocomplete follows the statement under the cursor. After `FROM`, `JOIN`,
`UPDATE`, `INTO` or `TABLE` it lists tables (as soon as you type the space).
In `SELECT`, `SET`, `WHERE`, `ON`, `ORDER BY`, `GROUP BY` and `HAVING` it lists
the columns of the tables the statement uses, wherever they appear: for
`UPDATE users SET … WHERE …` that is `users`' columns. After `alias.` or
`table.` it lists that table's columns, even when the `FROM` comes later
(`SELECT u.| FROM users u`). A column name shared by several joined tables is
offered qualified (`u.id`, `o.id`). Inside `INSERT INTO t (…)` it lists `t`'s
columns. Names that need quotes are inserted quoted. Tables, columns and keywords
are ranked in that order. Strings and comments get no suggestions.

Scripts are split client-side the way each engine's CLI does it: quotes,
comments, PostgreSQL `$$` bodies, the MySQL `DELIMITER` command and SQLite
trigger bodies are all handled. Each statement that returns rows gets a result tab, and
**Messages** lists every statement with its status, row count, time and any
error. Click a message to select that statement, or jump to the error
position. A run stops at the first error unless **Continue on error** is on.
Results show the first *Max rows* rows (1,000 by default, up to 50,000).
**Load more** fetches the next rows of the last statement's result from the
still-open cursor, so the query is never run twice.

Cancelling a PostgreSQL query keeps the tab's session. MySQL and MariaDB close
the connection when a query is cancelled. The next run then reconnects and tells
you that the session state (transaction, temporary tables, variables) is gone.

The text of each tab is saved per connection in the app's local storage and
comes back the next time you open that connection. Query history (every run, with time,
duration, rows and errors, but never passwords) is stored in `history.db`
next to `connections.json`, with the newest 10,000 runs kept per connection. Open
it with **History**: click an entry to insert it, double-click to open it in a
new tab. Queries run by an AI assistant (see "AI assistants (MCP)") are
marked **AI**.

### Formatting

**Format** (toolbar, Mod+Shift+F in the editor, or the command palette)
reformats the selection, or the whole script when nothing is selected, in the
connection's dialect (PostgreSQL, MySQL, MariaDB or SQLite). Keyword case
(UPPER, lower or as typed) and the indent (2 or 4 spaces) are set in
Settings. The change is a single edit, so Mod+Z undoes it, and the cursor stays
on the same token. Comments are kept. Scripts with a MySQL `DELIMITER`
command, and SQL the formatter cannot parse, are left unchanged with a short
message above the results. The formatter is
[sql-formatter](https://github.com/sql-formatter-org/sql-formatter), loaded on
first use.

### Opening and saving SQL files

**Open SQL file…** in the toolbar (or Mod+Shift+O) opens a `.sql` file in a
query tab, named after the file. If the file is already open, its tab is
shown; if the current tab is an empty, untitled query, the file goes there;
otherwise it gets a new tab. You can also drag `.sql` files from the file
manager onto the window: each one opens in a tab (other files are ignored).

**Save** in the query toolbar (or Mod+Shift+S) writes the tab back to its
file; a tab that has no file yet asks where to save it (the tab name is
suggested, and `.sql` is added when you type no extension). **Save SQL file
as…** in the command palette saves to another file. A ● on the tab and on
the Save button marks changes that are not saved yet. Closing such a tab asks
**Save**, **Don't save** or **Cancel**. Disconnecting keeps them: the tab,
with its unsaved changes and its file, comes back with the connection's
drafts.

Files are written atomically (to a temporary file that then replaces the
original) and keep their permissions and line endings (LF or CRLF). If the
file was changed by another program since it was opened or saved, Save asks
before overwriting it. Limits: UTF-8 text only (a byte order mark is accepted
but not written back), up to 10 MiB; other files are refused with a message.

### Query plans

**Explain** (Mod+Shift+E, or the toolbar) shows the query plan of the
selection or the statement under the cursor in a **Plan** tab next to the
results. It works on one `SELECT`, `WITH`, `TABLE`, `VALUES`, `INSERT`,
`UPDATE`, `DELETE`, `REPLACE` or `MERGE` statement and never runs it. It uses
the tab's connection, so temporary tables, `search_path` and an open
transaction apply. **Explain analyze** (toolbar or command palette) runs the
statement and adds the actual rows, loops and times. Because it runs the
statement, it only accepts reads: it is refused for anything that writes
(including `WITH … DELETE` and `SELECT … INTO`), in every safe mode. Explain
itself is allowed in every safe mode.

Each engine's plan is shown as the same collapsible tree: operation, object,
estimated rows, actual rows × loops, cost, time and each node's share of the
total time. Nodes that take at least 20% of the time are tinted, and ⚠ marks
row estimates that are 10× or more off. Click a node to see all its
properties; **Raw** shows the engine's own output.

| Engine | Explain | Explain analyze |
|---|---|---|
| PostgreSQL | `EXPLAIN (FORMAT JSON)` | `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` |
| MySQL | `EXPLAIN FORMAT=JSON` | `EXPLAIN ANALYZE` (TREE output, MySQL 8.0.18 or later) |
| MariaDB | `EXPLAIN FORMAT=JSON` | `ANALYZE FORMAT=JSON` |
| SQLite | `EXPLAIN QUERY PLAN` (the steps only: no row counts, costs or times) | Not available |

Copying is one click: **Copy** puts the plan on the clipboard as indented
text (one `-> Operation on object (est=…, actual=… × loops, cost=…, time=…)`
line per node, then the planning and execution times), ready for a chat,
issue or pull request. Its menu also has **Copy raw** (the engine's JSON or
text, for tools such as explain.dalibo.com), **Copy as Markdown table** and
**Copy query with EXPLAIN**. In the tree, Mod+C copies the selected node and
its subtree; right-click a node for **Copy node**, **Copy subtree** and
**Copy properties** (tab-separated). The arrow keys move through the tree and
expand or collapse nodes. Each Explain is recorded in the query history as
the EXPLAIN statement that ran.

## Editing data

Tables with a primary key can be edited in the grid. Views, tables without a
primary key and connections in read-only safe mode are read-only, and a banner
says why. Changes are staged, not written: modified cells are highlighted,
new rows are green, and rows marked for deletion are red and struck through.
The status bar shows "N pending changes" with **Discard**, **Preview SQL** and
**Commit**.

| Shortcut | Action |
|---|---|
| Double-click / Enter / typing | Edit the cell (type-aware editor: numbers, booleans, dates, JSON, enums, hex bytes) |
| Mod+S | Commit the staged changes |
| Mod+Z / Mod+Shift+Z | Undo / redo a staged change |
| Mod+N | Insert a row |
| Mod+D | Duplicate the selected row |
| Mod+Shift+N | Set the selected cells to NULL |
| Delete / Backspace | Mark the selected rows for deletion (again to unmark) |
| Right-click | Edit, Set NULL, Set DEFAULT, Set empty string, Insert, Duplicate, Delete |

Pasting tab-separated text fills a range of cells. Values cut for display
(text over 1 MiB, binary over 64 KiB) show a padlock and cannot be edited.
The row detail panel (Mod+I) edits the selected row too.

A commit runs every change in one transaction: deletes, then updates, then
inserts. Every value is sent as a bound parameter; the UI never sends SQL.
Each update and delete must hit exactly one row, found by its original
primary key. If a row was deleted or re-keyed elsewhere, or anything fails,
nothing is saved. The failing row is highlighted, and your changes stay staged.
**Preview SQL** shows a readable rendering of the statements, with a copy
button. Changing the page, sort or filter, refreshing, closing the tab,
switching database or disconnecting asks you to commit or discard first.

### Editing query results

Results in the SQL editor can be edited the same way when they come from a
plain `SELECT` on one table that includes its primary key, for example
`SELECT * FROM users WHERE active` or `SELECT id, name AS who FROM users`.
A badge next to the result tabs says **Editing users**, or **Read-only** with
the reason on hover (joins, `GROUP BY`/`DISTINCT`, subqueries in `FROM`,
`UNION`, views, a missing primary key column). Expression columns such as
`upper(name)` stay read-only, and an alias edits the column it names.
Unqualified table names are looked up in the connection's default schema.

The same shortcuts, status bar actions and safe-mode rules apply. After a
commit the statement runs again to show the saved rows. Commits use a separate
connection, so they are refused while the query tab has an open transaction:
run `COMMIT` or `ROLLBACK` first. Running the query again, switching to
another result set or closing the tab asks you to commit or discard first.

## Table structure

Every table tab has a **Data | Structure** switch at the bottom (**Mod+E**).
The structure view is read-only. Its header shows the table comment, the
estimated row count and the size (plus the engine and collation on
MySQL/MariaDB). It has these sections:

- **Columns**: type, nullable, default, auto-increment/identity/generated, collation, comment
- **Indexes**, including partial and expression indexes
- **Foreign keys** and **Referenced by**: click a table name to open it
- **Checks** (not reported by SQLite) and **Triggers**
- **DDL**: read-only, with **Copy** and **Open in new query tab**

Mod+R reloads the structure.

The DDL comes from `SHOW CREATE TABLE`/`VIEW` on MySQL/MariaDB and from
`sqlite_master` on SQLite. PostgreSQL has no built-in equivalent, so the
statement is rebuilt from the catalog. It covers columns, defaults,
identity, generated columns, serial columns, constraints, indexes, triggers
and comments. It leaves out ownership, grants, row-level security policies,
tablespaces, storage parameters, identity sequence options (start,
increment), inheritance, partitions (rendered as plain tables without
`PARTITION OF`), foreign-table servers and options, view options
(`security_barrier`, `CHECK OPTION`), index comments, and the definitions of
referenced types, sequences and functions.

**Foreign keys in the grid.** Foreign key columns have a link icon in their
header, and every non-NULL key cell shows a **→**. To open the referenced
row, click the arrow, press **Mod+O**, or choose **Open referenced row** from
the right-click menu. The referenced table opens in a tab, filtered by
`column = value` for each column of the key. The values are bound
parameters, like any filter. If that table's tab is already open, it is
reused, and you are asked to commit or discard first if it has staged
changes. A table in another schema opens as `schema.table`.

Right-click a table in the sidebar for **Open data**, **Open structure**,
**Copy name** and **Copy DDL**.

## Safe mode

Each connection has a safe mode, set in the connection form:

| Mode | Effect |
|---|---|
| Off | No restrictions |
| Confirm writes | The SQL editor shows the statements that write and asks before running them. Committing grid edits always opens the preview first. Imports and Run SQL file ask first. Choosing the Production tag suggests this mode. |
| Read-only | The session is read-only in the database itself (PostgreSQL `default_transaction_read_only`, MySQL `transaction_read_only`, MariaDB `tx_read_only`, SQLite `mode=ro`). Grid editing and importing are disabled, the editor's writes are rejected, and Run SQL file refuses files that write. |

The active mode is shown next to the connection name and applies from the
next connect. "Confirm" decides by each statement's leading keyword and
treats anything not clearly a read as a write, including `SET`. A `SELECT`
that calls a function with side effects is not detected. Read-only mode is a
guard against accidents, not a permission system: use database privileges
for that.

## AI assistants (MCP)

Lontar includes a [Model Context Protocol](https://modelcontextprotocol.io)
server, so Claude (Claude Code, Claude Desktop or any MCP client) can list,
explore and query the connections you choose. It is the same `lontar`
binary, started with `lontar mcp` by the client over stdio. It opens no
window and works whether or not the app is running. **Settings → AI
assistants (MCP)** shows the command for your installation, for example:

```sh
claude mcp add lontar -- /usr/bin/lontar mcp
```

For Claude Desktop, add the `mcpServers` entry shown there to
`claude_desktop_config.json`. On macOS the command is inside the bundle
(`/Applications/Lontar.app/Contents/MacOS/Lontar`); for an AppImage it is
the AppImage file.

Every connection starts with **AI access (MCP)** set to **Off** and is then
invisible to the assistant. Set it in the connection form:

| AI access | Claude can |
|---|---|
| Off | Nothing; the connection is not listed |
| Read | List databases, schemas, tables and objects, describe tables, get DDL, run read-only queries and explain them |
| Read and write | Also change data with `INSERT`, `UPDATE`, `DELETE`, `MERGE` or `REPLACE`, each change approved by you first |

The tools are `list_connections`, `list_databases`, `list_schemas`,
`list_tables`, `describe_table`, `list_objects`, `get_ddl`, `run_query`,
`explain_query` and `execute_write`. A resource,
`lontar://{connection}/schema`, gives Claude every table and column of a
connection's current schema in one document.

How it is kept safe:

- **Reads cannot write.** Claude's queries run on a separate session opened
  read-only in the database itself (as in read-only safe mode). Each
  statement runs in its own `READ ONLY` transaction, which is always rolled
  back. Statements that write, transaction control, `USE` and functions with
  effects outside the transaction (`pg_terminate_backend`, `set_config`,
  `nextval`, `dblink`, `lo_import`, `load_file`, `load_extension`, …) are
  refused before they reach the database.
- **Every write is shown to you first.** `execute_write` sends the exact SQL
  to your MCP client as an approval prompt. Nothing runs unless you approve
  it, and the approval only covers that SQL. Approved statements run in one
  transaction, and a failure rolls all of them back. DDL is never allowed. A
  client without approval prompts (MCP elicitation) cannot write. Read-only
  safe mode, and a read-only SQLite file, limit a connection to Read.
- **Limits:** 200 rows per statement by default (up to 1,000), at most 64 KB
  of output per call (long values are cut at 2,000 bytes), 60 seconds per
  call, and at most 8 KB of SQL per write. Sessions close after 10 minutes
  without use.
- **Nothing secret leaves Lontar.** Passwords, hosts, users and SSH settings
  are never shown to the assistant; it sees the connection's name, engine,
  default database, tag and access level. Query results do go to the AI
  provider, so only enable connections whose data you may share with it.
- **Everything is recorded.** Every query and change Claude runs goes into the
  connection's query history, marked **AI**.

Changes to a connection (including its AI access) apply to the next tool
call. An SSH host key that Lontar has not seen yet must be accepted once in
the app. Connections tagged Production are not treated differently, but
Claude is told their tag.

## SSH tunnels

The connection form's **SSH** tab connects through an SSH server (a
bastion). The database host and port are then reached *from the SSH
server*, so you can use names only it can resolve (e.g. `db.internal`).
Lontar opens no local port: every database connection is a forwarded
channel of one SSH connection, made in-process.

- **Authentication:** password, a private key file (`~/.ssh/id_ed25519`
  style paths work; encrypted keys need their passphrase), or the running
  SSH agent (`$SSH_AUTH_SOCK` on Linux/macOS, the OpenSSH agent service on
  Windows). The SSH password and the key passphrase are kept in the OS
  keychain like the database password, each under its own entry, and are
  never shown again ("saved", **Clear saved**).
- **Host keys are always checked.** Lontar reads `~/.ssh/known_hosts` (it
  never writes it) and its own `known_hosts` next to `connections.json`.
  - The first connection to an unknown server shows its key type and
    SHA256 fingerprint. Compare it with what the server's administrator
    gives you, then choose **Trust and connect**. The key is added to
    Lontar's own `known_hosts`.
  - If a server's key **changed**, Lontar refuses to connect and names the
    recorded entry. This can mean someone is intercepting the connection.
    If the change is expected (the server was reinstalled), delete that
    line from the named `known_hosts` file by hand and connect again.
    Lontar never replaces a known key itself.
- A keepalive is sent every 30 seconds. If the SSH connection drops, the
  running query fails with an error, and the next query reconnects the
  tunnel once. Switching databases reuses the tunnel; disconnecting closes it.
- **Test** goes through the tunnel too, including every jump host.
  Pageant (PuTTY's agent) is not supported.

### Jump hosts

When the SSH server is itself only reachable through other bastions, add
up to **3 jump hosts** under **Jump hosts** on the SSH tab (**Add jump
host**, **Remove**, and the ↑/↓ buttons to reorder). This is the same idea
as OpenSSH's `ProxyJump`, but configured in the form; `~/.ssh/config` is not
read.

- **Order:** jump host 1 is dialled first, directly from this machine. Each
  next hop is reached through the previous one, and the **SSH host** at the
  top of the tab is the *last* hop: the one that reaches the database. The
  chain is you → jump host 1 → jump host 2 → … → SSH host → database.
- Each hop has its own host, port, user and authentication (password,
  private key with **Browse…** and passphrase, or the SSH agent). Hop
  secrets are kept in the keychain like the others, each under its own
  entry, and stay with their hop when you reorder the list. Removing a hop
  (or the connection) removes its saved secrets.
- **Host keys are checked on every hop**, against the same `known_hosts`
  files. An unknown or changed key stops the chain at that hop, and the
  dialog names it (for example *jump host 2 (bastion2.example.com)*).
  Trusting it adds that hop's key to Lontar's `known_hosts`, and the next
  attempt continues to the next hop. A changed key is never replaced.
- Authentication and connection errors name the hop too. The connect
  timeout covers the whole chain.
- The keepalive runs on the last hop. If any hop drops, the whole chain is
  rebuilt on the next query; disconnecting closes it from the last hop back
  to the first.

Sessions through SSH show an **SSH** badge next to the connection name; with
jump hosts its tooltip shows the chain (`you → bastion1 → bastion2 → gw`).

## SSL/TLS

The **SSL** tab sets the TLS mode for PostgreSQL, MySQL and MariaDB (SQLite
has none):

| Mode | Meaning |
|---|---|
| Default | Uses the `sslmode` (PostgreSQL) or `tls` (MySQL/MariaDB) driver option if you set one, otherwise the driver default |
| Disable | No TLS |
| Preferred | MySQL/MariaDB only: TLS if the server offers it, not verified |
| Require | TLS or fail; the certificate is not verified, unless a CA file is set, which then verifies the chain like Verify CA |
| Verify CA | The server certificate must chain to the CA file (or the system roots); the host name is not checked |
| Verify full | Verify CA plus the host name must match the certificate (the connection's host, also through SSH) |

A mode other than Default **wins over** any `sslmode`/`tls` driver option. A
client certificate needs both the certificate and the key file (PEM). Use
**Browse…** or type the paths (`~` is expanded).

## Driver options

The **Advanced** tab (PostgreSQL, MySQL, MariaDB) takes extra driver options
as name/value rows, for example `allowCleartextPasswords` = `true` for MySQL
users that need cleartext authentication ("this user requires clear text
authentication"), or `application_name` for PostgreSQL. Options that have
their own field (host, port, user, password, database, ...) are rejected. Use
cleartext authentication only with TLS or an SSH tunnel.

## Export

**Export…** in the toolbar (also in the command palette) exports the active
tab:

- **Table tab:** every row of the table that matches the current filters,
  in the current sort order. Rows are streamed from the database, so large
  tables are fine.
- **Query result:** the rows already loaded, or **All rows**. All rows
  runs the statement again on a new connection. It is offered only for a
  single read-only statement that returns rows (never a write), runs in a
  read-only transaction, and the statement is shown before it runs.
  Session state from the query tab (temporary tables, `SET`) does not apply
  to it.
- **Selection:** right-click the grid → **Export selection…** writes the
  selected cells as TSV or CSV.

Formats:

- **CSV:** delimiter, header row, quote character, NULL as an empty field,
  `\N` or custom text, LF or CRLF line endings, and an optional UTF-8 BOM
  for Excel. Binary values are hex.
- **JSON:** an array of objects, or NDJSON. Big integers and decimals are
  strings, so they stay exact; "all numbers as strings" is optional. Bytes
  are hex or base64. NULL is `null`.
- **SQL INSERT:** for the connection's dialect, with rows per INSERT and an
  optional `CREATE TABLE` (table exports). Literals are written so that the
  file runs correctly whatever the server settings: PostgreSQL uses `E'…'`
  for strings with backslashes or control characters, and `decode(…,'hex')`
  for bytea. On MySQL/MariaDB, strings that contain a backslash, NUL or
  Ctrl-Z are written as `_utf8mb4 X'…'`, so the file gives the same data
  with and without the `NO_BACKSLASH_ESCAPES` SQL mode. Generated columns
  are left out.

The file is written to a temporary file next to the target and renamed
when complete. Cancelling, or an error, removes the temporary file and
leaves any existing file untouched. Exported files are created readable
only by you (mode 0600 on Linux/macOS).

## Importing CSV and JSON

**Import…** on a table tab loads a CSV, JSON or NDJSON file into that table:

1. Choose the file and its format. The format is detected (`.ndjson` and
   `.jsonl` are NDJSON; `.csv`, `.tsv` and `.txt` are CSV; otherwise a file
   starting with `[` is JSON and one starting with `{` is NDJSON) and can be
   overridden. For CSV, choose how to read it: delimiter, quote, header row,
   a NULL marker such as `\N`, empty fields as NULL, and rows to skip. Files
   must be UTF-8; a byte order mark is skipped.
   - **JSON** is an array of objects, read element by element (the file is
     never loaded whole). **NDJSON** has one object per line; blank lines are
     skipped.
   - The columns are the keys of the first 50 records, in the order they
     first appear. A key that only appears later is an error that names it.
     A key missing from a record is NULL.
   - Strings are used as they are, numbers as their exact text (no rounding),
     `true`/`false` as booleans, `null` as NULL, and nested objects and
     arrays as compact JSON text (for json, jsonb or text columns).
2. Check the preview (the first 50 rows) and the mapping. Columns (CSV
   header names or JSON keys) are matched to table columns by name, ignoring
   case. You can map any column to another one, or ignore it. Table columns
   without a mapping get their default.
3. **Import.** Every row is inserted in one transaction, with bound
   parameters and the same type handling as grid edits. Binary columns take
   hex. If any row fails, nothing is imported, and the error names the CSV or
   NDJSON line (or the JSON array element), and the column when the database
   says which. Cancelling rolls everything back too.

Read-only safe mode does not allow importing, and Confirm mode asks first.

## Running SQL files

**Run SQL file…** in the toolbar (or in the command palette) runs a `.sql`
file or database dump on the connection, statement by statement. The file is
streamed, so dumps of many gigabytes run without being loaded into memory.

1. Choose the file. Lontar shows its size, which tool wrote it and how many
   statements it has (counted exactly for files up to 8 MiB, estimated from
   the first 8 MiB otherwise), and warns when the dump looks like it is for
   another engine. Compressed files are refused: decompress them first.
2. Choose what happens on errors:
   - **Stop at the first error** (the default). What ran before it stays.
   - **Run in one transaction.** An error or Cancel rolls everything back.
     The file's own `BEGIN`/`COMMIT` statements are skipped. On MySQL and
     MariaDB, DDL statements (`CREATE`, `DROP`, `ALTER`, …) commit
     implicitly, so they cannot be rolled back.
   - **Continue after errors.** Every statement runs and the failures are
     listed at the end.
3. Follow the progress (how much of the file was read, statements run, rows
   copied) and cancel if needed. The result lists how many statements ran,
   failed and were skipped, and the errors with their line, the start of the
   statement and the database's message. Click an error to open the
   statement in a new query tab. The sidebar and the editor's completion are
   refreshed afterwards.

Supported files:

| Tool | Notes |
|---|---|
| `pg_dump` (plain format) | `COPY … FROM stdin` data blocks are sent with PostgreSQL's COPY protocol. pg_dump's `\restrict`/`\unrestrict` lines are skipped; other psql meta-commands (such as `\connect`) fail as errors. Custom, directory and tar formats need `pg_restore`. |
| `mysqldump`, `mariadb-dump` | `DELIMITER` blocks (triggers, routines, events) and `/*!…*/` version comments work. `DEFINER` clauses need the matching privileges. |
| `sqlite3 .dump` | Runs as written (it has its own transaction). |
| Any other SQL script | Split with the same rules as the SQL editor. |

The file runs on its own connection, which is closed afterwards, so the
settings a dump changes (search path, foreign key checks, …) do not affect
the rest of the session. A single statement may be at most 64 MiB (COPY data
is not limited); a larger one stops the run with an error. `COPY … FROM
stdin` only works on PostgreSQL; on MySQL and SQLite it is an ordinary
statement and fails.

Safe mode is enforced before anything runs: on a read-only connection a
file with any write statement is refused (the file is read up to the first
write), and on a Confirm connection the whole file is read first and the
number of writes and the first 20 of them are shown; it runs after you
confirm once.

### Switching connections

Press Mod+K, or click the connection name at the top of the sidebar, to
switch to another saved connection without going back to the connection list.
Connections stay open when you switch away: each keeps its tabs, query
results and staged edits, and switching back is instant (no reconnect). The
switcher lists the current connection first, then the other open ones; a
number next to the sidebar name shows how many are open.

A new connection opens before anything changes. If it fails, you stay where
you are and the reason is shown. **Disconnect** in the toolbar closes the
current connection and shows the next open one (or the connection list).
The × next to an open connection in the switcher closes it in the
background, after asking if it has staged edits that were not committed.

## Settings and themes

**Settings** (Mod+, or the gear button at the bottom left of the status bar)
are stored in `settings.json` next to `connections.json`. It is written
atomically and versioned. The dialog lists its sections on the left (Up/Down
move between them) and reopens on the one you used last:

- **Appearance:** the **theme**, System (follows the OS setting live), Dark or
  Light (the grid, editor and structure views switch too), and the **editor
  font size**.
- **SQL editor:** the default **max rows** (1,000) of new query tabs; **ask
  before closing a query tab with unrun changes** (a tab whose text is saved
  in its `.sql` file is not asked about); and **Format SQL**: keyword case
  (UPPER, lower or as typed) and indent (2 or 4 spaces) of **Format**.
- **Data & export:** **rows per page** of new table tabs (default 300) and
  the **CSV export defaults**.
- **Connections:** **Disconnect when idle for** Never (default), 5, 15 or 30
  minutes, or 1, 2 or 4 hours. A session unused for that long has its
  database connection (and SSH tunnel) closed but stays open: its tabs keep
  their state, the sidebar shows an **Idle** badge, and the next action
  reconnects with the saved settings, on the same database and with the same
  safe mode. A running query, an import, export or SQL file run, a query tab
  with an open transaction and a truncated result whose rows are still being
  fetched all keep the connection open. Query tabs reconnect on their next run
  and say so: their temporary tables and session settings (SET, USE,
  search_path) are gone. The MCP server (`lontar mcp`) has its own 10-minute
  idle limit.
- **AI assistants:** how to connect Claude to Lontar (see "AI assistants
  (MCP)").
- **Updates:** the installed version, **Install updates automatically** (on
  by default) and **Check for updates…** (see "Updates").

Changes in every section are kept until you **Save** or **Cancel**.

### Window and layout

Lontar remembers how you left it, in `state.json` next to `settings.json`:

- **The window:** its size, position and whether it was maximised. A window
  closed while maximised opens maximised and un-maximises to its previous
  size. A minimised or fullscreen window comes back as a normal window. If
  the saved position is off every screen (a monitor was unplugged), the
  window opens centred. On Wayland the compositor places the window, so only
  the size and maximised state are restored.
- **Panel sizes:** the sidebar, the row detail panel, the SQL editor/results
  split and the query history panel. Only sizes you drag are saved, not
  sizes that change because the window was resized.
- **Panel toggles:** whether the row detail and query history panels are open,
  and which sidebar groups are collapsed.
- **Table column widths**, per saved connection and table. Column widths in
  SQL editor results are not kept.

The window is saved when it is maximised or restored, and when Lontar quits.
Panel sizes and column widths are saved shortly after you change them.
Deleting `state.json` resets the layout; a corrupt file is ignored and
replaced.

## Updates

Lontar asks GitHub Releases for the latest **stable** release (pre-releases
are never offered) shortly after it starts and then every 6 hours.

- If a newer version exists and this installation can update itself (see the
  table below), Lontar downloads, verifies and installs it in the background
  and shows a small notice: **Restart…** opens the update dialog, where
  **Restart now** switches to the new version. If you ignore it, the new
  version runs the next time you start Lontar.
- If this installation cannot update itself (`.deb`, `.rpm`), the notice only
  says that a new version is available; **Details** shows why and links to
  the release page. A dismissed notice is not shown again for that version
  until Lontar restarts.
- Up to date, offline or rate limited: nothing is shown. Development builds
  never check on their own.

Turn this off with **Install updates automatically** in Settings (on by
default). Lontar then only checks when you ask.

To check by hand, use **Check for updates…** in Settings or in the command
palette. It shows the latest version and its release notes.

If a newer version exists, **Download and install** downloads it in the
background and shows the progress (**Cancel download** stops it). Lontar
installs nothing unless both of these checks pass:

- the release's `SHA256SUMS.sig` is a valid ed25519 signature of
  `SHA256SUMS`, made with the release key whose public half is built into
  Lontar;
- the downloaded file matches its line in `SHA256SUMS`.

Once installed, **Restart now** starts the new version and quits this one.
Open connections are closed, and staged changes that were not committed and
unsaved query text are lost. **Later** keeps the current version running
until you quit it.

| Installed from | What is replaced |
|---|---|
| AppImage (x86_64) | The `.AppImage` file itself |
| Windows installer or portable zip (x64) | `lontar.exe`. The old exe is kept as `lontar.exe.old` and deleted at the next start. The version shown in "Apps & features" keeps the originally installed number. |
| macOS `.dmg` | The `Lontar.app` bundle, taken from the new `.dmg` |
| `.deb` / `.rpm`, development builds, other CPUs | Nothing. Lontar says why and offers the **Release page**; update with your package manager. |

Lontar needs write access to the installed file or bundle. A per-machine
install in Program Files, or an `.app` owned by another user, reports a
permission error and offers the release page instead.

## Saved connections and passwords

Connections are stored as JSON (schema-versioned, written atomically, file
mode `0600` in a `0700` directory) in the per-user config directory:

| OS | Location |
|---|---|
| Linux | `$XDG_CONFIG_HOME/lontar/connections.json` (default `~/.config/lontar/`) |
| Windows | `%AppData%\lontar\connections.json` |
| macOS | `~/Library/Application Support/lontar/connections.json` |

**Passwords (database, SSH password, SSH key passphrase, and those of every
jump host) are never written to `connections.json`** and are never sent back to the UI (it only learns whether
one is saved). They are kept in the OS
keychain via [go-keyring](https://github.com/zalando/go-keyring), under the
service `lontar` with the connection ID as the account (SSH and jump host
secrets use `<id>:<purpose>`, e.g. `<id>:ssh.jump.<hop id>.password`, where
the hop ID is a stable identifier of the jump host, not its position):

- macOS: Keychain
- Windows: Credential Manager
- Linux: Secret Service (gnome-keyring, KWallet, KeePassXC, ...)

**Linux fallback.** If no Secret Service is reachable (e.g. a minimal window
manager or a headless session), passwords are stored in `secrets.enc` in the
same directory, encrypted with AES-256-GCM. The key lives next to it in
`secrets.key` (mode `0600`). **This is weaker than an OS keychain:** anyone
who can read your files can decrypt it. It only keeps passwords out of
`connections.json` and out of casual view. Start a Secret Service to avoid
the fallback; passwords saved later go to the keychain, and the stale
fallback copy is then removed. On macOS and Windows there is no fallback, and
keychain errors are reported.

Deleting a connection also deletes its saved passwords. `connections.json` is
at schema version 3 (M6); jump hosts are an optional `ssh.jumps` list in the
same version, so connections without them are unchanged. Older files are upgraded on the next save, and a file
from a newer Lontar is refused rather than overwritten.

### Upgrading from dbedit

Lontar was called dbedit. On its first start it moves dbedit's data over:

- **Config directory.** `dbedit/` in the per-user config directory (with
  `connections.json`, `history.db`, `settings.json`, `known_hosts` and the
  Linux fallback `secrets.enc`/`secrets.key`) is renamed to `lontar/`. If
  that fails (e.g. it would cross file systems) it is copied, keeping the
  file permissions, and the old directory is removed only after the copy
  succeeded. Nothing is moved when `lontar/` already exists; the old
  directory is then left alone and a line is logged. If the move fails,
  Lontar uses `dbedit/` for that run and tries again on the next start.
- **Passwords in the OS keychain** move from the service `dbedit` to
  `lontar` the first time each one is needed. Saving or deleting a password
  also removes any copy left under `dbedit`. On macOS the keychain may ask
  once whether Lontar may read an item that dbedit created.
- **Unsent query drafts** are not carried over in the desktop app. The
  webview keeps its local storage under the program name
  (`~/.local/share/dbedit` on Linux, `%AppData%\dbedit.exe` on Windows, the
  `dev.dbedit.app` WebKit data on macOS), so Lontar starts with an empty
  one. (`dbedit.*` keys are moved to `lontar.*` where the storage is shared,
  e.g. server mode in a browser.) The old webview directories can be deleted
  by hand.

On Windows, uninstall dbedit before or after installing Lontar: the two are
separate entries in "Apps & features". Uninstalling dbedit keeps the data
that Lontar has already moved.

## Installing

Download the file for your OS from the project's GitHub Releases page. Check
it against `SHA256SUMS` from the same release (`sha256sum -c SHA256SUMS
--ignore-missing` on Linux, `shasum -a 256 -c SHA256SUMS --ignore-missing` on
macOS, `Get-FileHash` on Windows).

| OS | File | Notes |
|---|---|---|
| Linux (Debian 13+, Ubuntu 24.04+) | `lontar-<version>-linux-amd64.deb` | `sudo apt install ./lontar-*.deb` pulls in GTK4 (`libgtk-4-1`) and WebKitGTK 6.0 (`libwebkitgtk-6.0-4`). |
| Linux (Fedora 39+) | `lontar-<version>-linux-x86_64.rpm` | `sudo dnf install ./lontar-*.rpm` pulls in `gtk4` and `webkitgtk6.0`. |
| Linux (any, x86_64) | `lontar-<version>-linux-x86_64.AppImage` | `chmod +x lontar-*.AppImage && ./lontar-*.AppImage`. Self-contained (GTK and WebKitGTK bundled), so it is large (~130 MB). |
| Windows 10/11 (x64) | `lontar-<version>-windows-amd64-setup.exe` | Per-user installer, see below. |
| Windows (portable) | `lontar-<version>-windows-amd64-portable.zip` | Just `lontar.exe`; needs the WebView2 runtime (built into Windows 11). |
| macOS 12+ (Apple silicon and Intel) | `lontar-<version>-macos-universal.dmg` | Open it and drag Lontar to Applications. |

The packages install `lontar` to `/usr/bin`, a desktop entry
(`Development;Database;`) and the icon in the `hicolor` theme. The optional
`gnome-keyring` recommendation provides the Secret Service; without one,
Lontar stores passwords in its encrypted file instead (see "Saved connections
and passwords").

**Finding Lontar in Spotlight (macOS).** Besides its name, Spotlight finds
Lontar by what it does: "db", "database", "sql", "query", "postgres",
"mysql", "mariadb", "sqlite" and similar. Lontar writes these keywords onto
its own `Lontar.app` the first time it starts (and again after an update
replaces the bundle), as Spotlight metadata (`kMDItemKeywords`) and a Finder
comment. The comment is only added when the app has none, so one you wrote
in **Get Info → Comments** is kept; anything you write there is searchable
too. The metadata sits on the bundle folder, outside the code signature. If
Lontar may not write to the bundle (installed by another user, or still
running from the download before being moved to Applications), it just
skips this.

**Windows installer.** It installs **per user** into
`%LOCALAPPDATA%\Programs\Lontar` (no administrator prompt), adds a Start-menu
and a desktop shortcut and an "Apps & features" entry with an uninstaller.
If the Microsoft Edge WebView2 runtime is missing it runs Microsoft's
Evergreen bootstrapper, which downloads the runtime (**internet access
needed** for that step only; Windows 11 and current Windows 10 already have
it). Uninstalling removes the program and the WebView2 cache
(`%AppData%\lontar.exe`) but keeps your connections, history and settings in
`%AppData%\lontar` and the passwords in Credential Manager.

**Unsigned builds.** Releases are only code-signed when the maintainers'
signing secrets are configured (see "Releasing"). Unsigned builds work, but
the OS warns first:

- **Windows:** SmartScreen shows "Windows protected your PC". Click
  **More info → Run anyway**.
- **macOS:** Gatekeeper says the app "cannot be opened because the developer
  cannot be verified" (or that it is "damaged"). Either right-click (Control-
  click) Lontar in Applications, choose **Open** and confirm **Open**
  (on macOS 15+: try to open it once, then **System Settings → Privacy &
  Security → Open Anyway**), or remove the quarantine flag:
  `xattr -dr com.apple.quarantine /Applications/lontar.app`.
- **Linux:** packages are not GPG-signed; verify them with `SHA256SUMS`.

## Build

```sh
wails3 build          # production binary in bin/ (version-stamped)
wails3 task version   # the version builds are stamped with
```

### Versioning

Every build and package task stamps the same version (`VERSION` in the root
`Taskfile.yml`) into the Go binary (`-ldflags -X
lontar/internal/services.Version=…`, shown in the status bar), the macOS
`Info.plist`, the Windows VERSIONINFO resource and installer, and the
`.deb`/`.rpm` metadata. It comes from:

1. `LONTAR_VERSION` if set (a leading `v` is dropped), e.g.
   `LONTAR_VERSION=v26.11.1 wails3 task package:linux`; otherwise
2. `git describe --tags --always --dirty`: tag `v26.11.1` → `26.11.1`,
   `v26.11.1-4-gabc1234` → `26.11.1-4-gabc1234`, an untagged commit →
   `0.0.0-dev+<hash>[-dirty]`; otherwise
3. `0.0.0-dev` (no git), which is also the default of a plain `go build`.

Fields that only take numbers (`CFBundleVersion`, Windows file version, NSIS)
get the `X.Y.Z` core. `build/config.yml`'s `version` is only a baseline.

### Building packages

Packages are built natively on each OS (the release workflow does this on
GitHub's runners). Output goes to `bin/`.

| Task | Host | Output | Extra tools |
|---|---|---|---|
| `wails3 task package:linux` | Linux | `lontar-x86_64.AppImage`, `lontar.deb`, `lontar.rpm`, `lontar.pkg.tar.zst` | none: nfpm is built into `wails3`; the AppImage step downloads linuxdeploy (internet). |
| `wails3 task package:windows` | Windows (or Linux with `GOOS=windows`) | `lontar-amd64-installer.exe` | [NSIS](https://nsis.sourceforge.io) `makensis` on `PATH`; the WebView2 bootstrapper is downloaded. `INSTALL_SCOPE=machine` builds a per-machine (Program Files, UAC) installer instead. |
| `wails3 task package:darwin` | macOS | universal `lontar.app` + `lontar.dmg` | Xcode command line tools. The app is ad-hoc signed only. |

`GOOS=windows wails3 build` cross-compiles `bin/lontar.exe` (with icon,
manifest and version resource) from Linux or macOS, since the Windows build
needs no cgo. The macOS and Linux GUI builds need cgo and so their own OS (or
the `wails3 task setup:docker` cross-compile image).

Identity (name, publisher `Lontar contributors`, bundle id `dev.lontar.app`,
description, copyright) is set in `build/config.yml`. After changing it run
`wails3 task common:update:build-assets`, then re-apply what that command
overwrites from the Wails templates: `build/linux/nfpm/nfpm.yaml` (Lontar's
dependencies, icons, `Apache-2.0` license and the LICENSE/NOTICE files) and the hand-added keys in
`build/darwin/Info*.plist` (the comment block, `LSApplicationCategoryType`,
`LSMinimumSystemVersion` 12.0, the boolean `NSHighResolutionCapable`, and
`CFBundleDisplayName` "Lontar"); restore `build/darwin/entitlements.plist`,
which it deletes; delete the `build/ios` and `build/linux/desktop` files it
recreates (unused). `build/linux/dev.lontar.app.desktop` is maintained by hand;
its name must stay equal to the GTK application id (`applicationID` in
`app.go`), which is the Wayland app_id docks use to find the icon.

### Regenerating the icon

`build/appicon.svg` is the only source of the icon. After editing it run:

```sh
wails3 task icons:render
```

This renders it with `tools/iconrender` (pure Go, `oksvg`; keep to paths,
basic shapes and gradients) into `build/appicon.png` (1024²), the Linux
`hicolor` PNGs (16–512) and scalable SVG, the favicon
(`frontend/public/favicon.svg`) and the dmg icon/background, then rebuilds
`build/windows/icon.ico` and `build/darwin/icons.icns` with `wails3 generate
icons`. Commit the results; builds do not re-render.

## Releasing

Releases use calendar versioning: **`vYY.MM.MICRO`**, with the two-digit
year, the month without a leading zero, and a counter that restarts at 1 every
month (`v26.11.1`, `v26.11.2`, `v26.12.1`). A pre-release adds a suffix,
`v26.11.3-rc.1`; it does not use up its number, so `v26.11.3` follows it.
`tools/calver` checks the format; tags in any other format fail the release.

1. Make sure CI is green on `main`.
2. Tag and push the next version:
   ```sh
   git fetch --tags
   wails3 task release:next          # e.g. 26.11.2
   git tag v26.11.2 && git push origin v26.11.2
   ```
3. `.github/workflows/release.yml` checks the version, runs the short tests
   on Linux, Windows and macOS, builds every package stamped with `26.11.2`,
   signs what it has secrets for, and creates a **draft** GitHub Release with
   the files and `SHA256SUMS` (versions with a `-` are marked pre-release).
4. Review the draft and publish it.

The workflow can also be started by hand (**Actions → Release → Run
workflow**). If you leave the version empty, it uses the next number for the
current month (UTC), based on the existing tags and releases. You can also
enter a version such as `26.11.2-rc.1`. The draft targets the dispatched
commit, with tag `v<version>`. The run fails if that tag or a release (even a
draft) for it already exists, so publish or delete a draft before starting
another run. `wails3 task release:checksums DIR=dist` writes the same
`SHA256SUMS` locally.

Signing is optional; each step is skipped when its secrets are missing:

| Secret | Used for |
|---|---|
| `WINDOWS_CERT_PFX` | Base64 of the Authenticode code-signing certificate (`.pfx`) |
| `WINDOWS_CERT_PASSWORD` | Its password |
| `MACOS_CERT_P12` | Base64 of the "Developer ID Application" certificate + key (`.p12`) |
| `MACOS_CERT_PASSWORD` | Its password |
| `APPLE_API_KEY` | Notarization, preferred: contents of an App Store Connect API key (`AuthKey_<KeyID>.p8`) |
| `APPLE_API_KEY_ID` | Its Key ID |
| `APPLE_API_ISSUER` | The Issuer ID (team keys; leave unset for an individual key) |
| `APPLE_ID` | Notarization, alternative: the Apple ID's e-mail |
| `APPLE_TEAM_ID` | The Apple Developer team ID |
| `APPLE_APP_PASSWORD` | An app-specific password for that Apple ID |
| `UPDATE_SIGNING_KEY` | ed25519 private key that signs `SHA256SUMS` into `SHA256SUMS.sig` for in-app updates (see below) |

**In-app update key.** Generate the key pair once:

```sh
go -C tools run ./updatesign keygen
```

Paste the public key into `PublicKey` in `internal/update/update.go` and
commit it. Store the private key as the `UPDATE_SIGNING_KEY` secret, and keep
an offline backup: if it is lost, installed versions can no longer update
themselves. The release job signs `SHA256SUMS` and checks the signature
against the committed public key. Without the secret the release is still
published, but a warning says that it cannot be installed from inside Lontar.
A build with an empty `PublicKey` can check for updates but never installs
one. To check a release by hand, run
`go -C tools run ./updatesign verify <public key> SHA256SUMS SHA256SUMS.sig`.

Windows signs `lontar.exe` before it goes into the installer, then the
installer (`build/windows/sign.ps1`, signtool, SHA-256 + RFC 3161 timestamp).
macOS signs the app with the hardened runtime and
`build/darwin/entitlements.plist` (only `com.apple.security.network.client`,
Wails' production preset), then signs, notarizes (`notarytool`) and staples
the dmg (`build/darwin/sign-notarize.sh`). Notarization uses the API key when
`APPLE_API_KEY` and `APPLE_API_KEY_ID` are set, otherwise the three `APPLE_*`
Apple ID secrets; with neither, the dmg is signed but not notarized. Before
uploading, the script checks the secrets' format and tries the credentials,
so a wrong secret is reported by name. It retries when Apple's service
answers HTTP 5xx. The `.app` targets macOS 12 (`LSMinimumSystemVersion`,
matching `-mmacosx-version-min=12.0`).

Setting up the macOS secrets (Apple Developer account):

1. Create a **Developer ID Application** certificate. Note that this is not
   "Apple Development" or "Mac App Distribution".
   - On a Mac: Xcode → Settings → Accounts → Manage Certificates → **+**.
   - Without a Mac: create the key and request with
     `openssl req -new -newkey rsa:2048 -nodes -keyout developerID.key -out developerID.csr -subj "/CN=Your Name"`,
     then upload the `.csr` on developer.apple.com → Certificates → **+** →
     Developer ID Application (G2 Sub-CA).
2. Make the `.p12` with the certificate *and its private key*, and store
   `base64 -w0 DeveloperID.p12` as `MACOS_CERT_P12` and its password as
   `MACOS_CERT_PASSWORD`.
   - On a Mac: export from Keychain Access → My Certificates.
   - Without a Mac: convert the downloaded `.cer` and Apple's
     [Developer ID G2 CA](https://www.apple.com/certificateauthority/DeveloperIDG2CA.cer)
     to PEM (`openssl x509 -inform DER -in … -out ….pem`), then run
     `openssl pkcs12 -export -inkey developerID.key -in developerID.pem -certfile DeveloperIDG2CA.pem -keypbe PBE-SHA1-3DES -certpbe PBE-SHA1-3DES -macalg sha1 -out DeveloperID.p12`.
     The legacy encryption flags are needed because macOS's `security import`
     does not reliably read OpenSSL 3's default `.p12` format.
3. Notarization credentials. Use either of these:
   - **App Store Connect API key (recommended):** go to appstoreconnect.apple.com
     → Users and Access → Integrations → App Store Connect API, and create a
     *Team Key* with the **Developer** role. Download the `.p8`; Apple only
     offers the download once. Then set:
     - `APPLE_API_KEY`: the file's contents, e.g.
       `gh secret set APPLE_API_KEY < AuthKey_XXXXXXXXXX.p8`
     - `APPLE_API_KEY_ID`: the key's Key ID
     - `APPLE_API_ISSUER`: the Issuer ID shown above the key list
   - **Apple ID:** create an app-specific password on account.apple.com →
     Sign-In and Security → App-Specific Passwords and store it as
     `APPLE_APP_PASSWORD`. `APPLE_ID` is the account's e-mail, and
     `APPLE_TEAM_ID` is the 10-character Team ID shown on
     developer.apple.com → Membership.
4. Add the secrets under **Settings → Secrets and variables → Actions** of
   the GitHub repository, or with `gh secret set NAME`.

## Website

`website/` holds the marketing site: a home page and a download page. It is
a static [Astro](https://astro.build) site and a separate npm project.

```sh
wails3 task website:dev     # http://localhost:4321 with hot reload
wails3 task website:test    # Vitest, fails below 80% coverage
wails3 task website:build   # astro check + static build into website/dist
```

The download page asks the GitHub API for the latest **stable** release (the
same endpoint the updater uses), detects the visitor's OS and links straight
to the matching file. The result is cached for the browser session. Before
the API answers, without JavaScript, or when GitHub is unreachable or
rate-limited, every button links to the latest release page instead. File
names are matched against the patterns in "Installing", so keep
`website/src/lib/releases.ts` in step if those names change.

It is deployed as a Cloudflare Worker that serves only static files
(`website/wrangler.jsonc`: assets from `dist/`, unknown paths get the 404
page). In the Worker's build settings, use path `website`, build command
`npm run build`, deploy command `npx wrangler deploy`, and the build
variables `NODE_VERSION=24` and `SITE_URL` (the site's public URL, so
canonical and social-preview URLs are absolute). By hand:
`cd website && npm run build && npx wrangler deploy`. Netlify or Vercel work
too: root directory `website`, build command `npm run build`, output `dist`.
No server code is involved.
