# Lontar

A fast, lightweight desktop database client for PostgreSQL, MySQL/MariaDB and
SQLite, built with Go + [Wails 3](https://v3.wails.io) and React/TypeScript.

Lontar are the palm-leaf manuscripts once used in Bali and Java to record knowledge.

*Formerly dbedit.* Lontar moves your existing connections, passwords and
history over on first start; see "Upgrading from dbedit".

## Prerequisites

All platforms:

- Go 1.26+
- Node.js 24+ and npm
- Wails 3 CLI: `go install github.com/wailsapp/wails/v3/cmd/wails3@v3.0.0`
- Docker (or Podman with the Docker API socket) — only for the database
  integration tests

Per OS:

| OS | Requirements |
|---|---|
| Linux | C toolchain + GTK4/WebKitGTK 6.0 dev packages. Debian/Ubuntu: `sudo apt install build-essential pkg-config libgtk-4-dev libwebkitgtk-6.0-dev`. (The legacy GTK3 stack, `libgtk-3-dev libwebkit2gtk-4.1-dev`, is used only when building with `-tags gtk3`.) |
| Windows | Microsoft Edge WebView2 runtime (preinstalled on Windows 10 21H2+/11; otherwise install the Evergreen runtime). |
| macOS | Xcode Command Line Tools: `xcode-select --install`. |

Run `wails3 doctor` to check your setup.

## Development

```sh
cd frontend && npm install && cd ..
wails3 dev            # hot-reloading app (Go + Vite)
```

Bindings for Go services live in `frontend/bindings/` and are generated — do
not edit them by hand. Regenerate after changing a bound service:

```sh
wails3 generate bindings -clean=true -ts -i
```

## Tests

Tasks are run with Wails' bundled task runner (`wails3 task <name>`; a
standalone `task` binary works too):

| Task | What it does |
|---|---|
| `wails3 task test` | Go + frontend + `tools/` tests |
| `wails3 task test:go` | `go test ./... -coverprofile=coverage.out`, including container integration tests (needs Docker) |
| `wails3 task test:go:short` | Go unit tests only (`-short`, no Docker) |
| `wails3 task test:fe` | `vitest run --coverage` (fails below 80%) |
| `wails3 task cover` | Prints Go coverage and fails if the total (excluding `main.go`) is below 80% |
| `wails3 task test:tools` | Tests the build helpers in `tools/` (a separate Go module; also part of `test`) |

SSH tests use an in-process SSH server (`internal/sshtest`) and never touch
`~/.ssh`. TLS tests start their own PostgreSQL and MySQL containers with
certificates generated by `internal/tlstest`. Cross-platform vet: `GOOS=windows
go vet ./...`, `GOOS=darwin go vet ./internal/...` and `GOOS=darwin go vet -tags
server ./...`. The root package's darwin GUI build needs cgo, so it can only be
vetted on macOS.

Integration tests use `internal/testutil`, which starts PostgreSQL 16, MySQL 8
and MariaDB 11 with testcontainers-go (once per package via `SharedPostgres(t)`
etc. plus `testutil.Main` in `TestMain`) and provides `SQLiteTemp(t)` for
SQLite. They skip automatically with `-short` or when Docker is unreachable.

With rootless Podman, start the API socket first and point `DOCKER_HOST` at it:

```sh
systemctl --user start podman.socket
export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/podman/podman.sock
```

The SQL splitter has a fuzz test. Normal runs use only its seed corpus; to fuzz
locally, run `go test -run XXX -fuzz FuzzSplit -fuzztime 60s ./internal/sqlsplit`.

Integration tests share a fixture, `testutil.SeedBrowse`. It holds every
value type, a view, tables with no or a composite primary key, and a table
and columns with awkward names. Run it against each engine (SQLite always;
PostgreSQL, MySQL and MariaDB when Docker is available). The structure tests
add `testutil.SeedStructure`: composite and self-referencing foreign keys, a
cross-schema key (PostgreSQL), partial, expression and GIN indexes, checks,
generated and identity columns, comments, triggers and views. On PostgreSQL,
the reconstructed DDL is executed in a fresh schema and must give the same
structure back.

## Browsing tables

After connecting, the sidebar lists the tables and views of the current
schema. Switch databases (PostgreSQL, MySQL/MariaDB) or schemas
(PostgreSQL, attached SQLite databases) at the top. A single click previews
a table in a reusable tab, and a double click keeps it open. Rows load in
pages of 300. The status bar shows the server's row estimate until the
exact count is known.

| Shortcut | Action |
|---|---|
| Mod+R | Refresh the table list and the current tab |
| Mod+F | Toggle the filter bar (Enter applies) |
| Mod+I / Space | Toggle the row detail panel |
| Mod+C | Copy the selected cells as TSV |
| Mod+W | Close the tab |
| Mod+1 … Mod+9 | Switch tabs (Mod+9 = last) |

Click a column header to sort it (ascending, then descending, then off).
Shift-click adds a secondary sort. Filter values are always sent as bound
parameters. The filter bar's **Raw SQL** mode instead takes a WHERE
condition you type, and uses it verbatim against your database.

## SQL editor

**Mod+T** (or **New query**) opens an SQL tab next to the table tabs. Double-click
a tab to rename it. Each tab has its own database connection, kept from the first
run until the tab is closed. That means `BEGIN`/`COMMIT`, `SET`, `USE`,
`SET search_path` and temporary tables carry over from one run to the next. The
connection is also released when you disconnect or switch databases in the
sidebar, and after 30 minutes without a run. An open transaction is rolled back
whenever the connection is released. The toolbar shows **Transaction open**
while one is active. On MySQL, MariaDB and SQLite this is inferred from the
statements you run, so it is marked "(guess)".

| Shortcut | Action |
|---|---|
| Mod+Enter | Run the selection, or the statement under the cursor (highlighted) |
| Mod+Shift+Enter | Run the whole script |
| Esc | Stop the running query |
| Mod+F | Search in the editor (in a table tab it opens the filter bar) |
| Ctrl+Space / typing | Autocomplete tables, columns, `alias.column` and keywords (see below) |

Autocomplete follows the statement under the cursor. After `FROM`, `JOIN`,
`UPDATE`, `INTO` or `TABLE` it lists tables (as soon as you type the space).
In `SELECT`, `SET`, `WHERE`, `ON`, `ORDER BY`, `GROUP BY` and `HAVING` it lists
the columns of the tables the statement uses, wherever they appear: for
`UPDATE users SET … WHERE …` that is `users`' columns. After `alias.` or
`table.` it lists that table's columns, even when the `FROM` comes later
(`SELECT u.| FROM users u`). A column name shared by several joined tables is
offered qualified (`u.id`, `o.id`). Inside `INSERT INTO t (…)` it lists `t`'s
columns. Names that need quotes are inserted quoted. Tables, columns and keywords
are ranked in that order. Strings and comments get no suggestions.

Scripts are split client-side the way each engine's CLI does it: quotes,
comments, PostgreSQL `$$` bodies, the MySQL `DELIMITER` command and SQLite
trigger bodies are all handled. Each statement that returns rows gets a result tab, and
**Messages** lists every statement with its status, row count, time and any
error. Click a message to select that statement, or jump to the error
position. A run stops at the first error unless **Continue on error** is on.
Results show the first *Max rows* rows (1,000 by default, up to 50,000).
**Load more** fetches the next rows of the last statement's result from the
still-open cursor, so the query is never run twice.

Cancelling a PostgreSQL query keeps the tab's session. MySQL and MariaDB close
the connection when a query is cancelled. The next run then reconnects and tells
you that the session state (transaction, temporary tables, variables) is gone.

The text of each tab is saved per connection in the app's local storage and
comes back the next time you open that connection. Query history (every run, with time,
duration, rows and errors, but never passwords) is stored in `history.db`
next to `connections.json`, with the newest 10,000 runs kept per connection. Open
it with **History**: click an entry to insert it, double-click to open it in a
new tab.

## Editing data

Tables with a primary key can be edited in the grid. Views, tables without a
primary key and connections in read-only safe mode are read-only, and a banner
says why. Changes are staged, not written: modified cells are highlighted,
new rows are green, and rows marked for deletion are red and struck through.
The status bar shows "N pending changes" with **Discard**, **Preview SQL** and
**Commit**.

| Shortcut | Action |
|---|---|
| Double-click / Enter / typing | Edit the cell (type-aware editor: numbers, booleans, dates, JSON, enums, hex bytes) |
| Mod+S | Commit the staged changes |
| Mod+Z / Mod+Shift+Z | Undo / redo a staged change |
| Mod+N | Insert a row |
| Mod+D | Duplicate the selected row |
| Mod+Shift+N | Set the selected cells to NULL |
| Delete / Backspace | Mark the selected rows for deletion (again to unmark) |
| Right-click | Edit, Set NULL, Set DEFAULT, Set empty string, Insert, Duplicate, Delete |

Pasting tab-separated text fills a range of cells. Values cut for display
(text over 1 MiB, binary over 64 KiB) show a padlock and cannot be edited.
The row detail panel (Mod+I) edits the selected row too.

A commit runs every change in one transaction: deletes, then updates, then
inserts. Every value is sent as a bound parameter; the UI never sends SQL.
Each update and delete must hit exactly one row, found by its original
primary key. If a row was deleted or re-keyed elsewhere, or anything fails,
nothing is saved. The failing row is highlighted, and your changes stay staged.
**Preview SQL** shows a readable rendering of the statements, with a copy
button. Changing the page, sort or filter, refreshing, closing the tab,
switching database or disconnecting asks you to commit or discard first.

### Editing query results

Results in the SQL editor can be edited the same way when they come from a
plain `SELECT` on one table that includes its primary key, for example
`SELECT * FROM users WHERE active` or `SELECT id, name AS who FROM users`.
A badge next to the result tabs says **Editing users**, or **Read-only** with
the reason on hover (joins, `GROUP BY`/`DISTINCT`, subqueries in `FROM`,
`UNION`, views, a missing primary key column). Expression columns such as
`upper(name)` stay read-only, and an alias edits the column it names.
Unqualified table names are looked up in the connection's default schema.

The same shortcuts, status bar actions and safe-mode rules apply. After a
commit the statement runs again to show the saved rows. Commits use a separate
connection, so they are refused while the query tab has an open transaction:
run `COMMIT` or `ROLLBACK` first. Running the query again, switching to
another result set or closing the tab asks you to commit or discard first.

## Table structure

Every table tab has a **Data | Structure** switch at the bottom (**Mod+E**).
The structure view is read-only. Its header shows the table comment, the
estimated row count and the size (plus the engine and collation on
MySQL/MariaDB). It has these sections:

- **Columns**: type, nullable, default, auto-increment/identity/generated, collation, comment
- **Indexes**, including partial and expression indexes
- **Foreign keys** and **Referenced by**: click a table name to open it
- **Checks** (not reported by SQLite) and **Triggers**
- **DDL**: read-only, with **Copy** and **Open in new query tab**

Mod+R reloads the structure.

The DDL comes from `SHOW CREATE TABLE`/`VIEW` on MySQL/MariaDB and from
`sqlite_master` on SQLite. PostgreSQL has no built-in equivalent, so the
statement is rebuilt from the catalog. It covers columns, defaults,
identity, generated columns, serial columns, constraints, indexes, triggers
and comments. It leaves out ownership, grants, row-level security policies,
tablespaces, storage parameters, identity sequence options (start,
increment), inheritance, partitions (rendered as plain tables without
`PARTITION OF`), foreign-table servers and options, view options
(`security_barrier`, `CHECK OPTION`), index comments, and the definitions of
referenced types, sequences and functions.

**Foreign keys in the grid.** Foreign key columns have a link icon in their
header, and every non-NULL key cell shows a **→**. To open the referenced
row, click the arrow, press **Mod+O**, or choose **Open referenced row** from
the right-click menu. The referenced table opens in a tab, filtered by
`column = value` for each column of the key. The values are bound
parameters, like any filter. If that table's tab is already open, it is
reused, and you are asked to commit or discard first if it has staged
changes. A table in another schema opens as `schema.table`.

Right-click a table in the sidebar for **Open data**, **Open structure**,
**Copy name** and **Copy DDL**.

## Safe mode

Each connection has a safe mode, set in the connection form:

| Mode | Effect |
|---|---|
| Off | No restrictions |
| Confirm writes | The SQL editor shows the statements that write and asks before running them. Committing grid edits always opens the preview first. Choosing the Production tag suggests this mode. |
| Read-only | The session is read-only in the database itself (PostgreSQL `default_transaction_read_only`, MySQL `transaction_read_only`, MariaDB `tx_read_only`, SQLite `mode=ro`). Grid editing is disabled and the editor's writes are rejected. |

The active mode is shown next to the connection name and applies from the
next connect. "Confirm" decides by each statement's leading keyword and
treats anything not clearly a read as a write, including `SET`. A `SELECT`
that calls a function with side effects is not detected. Read-only mode is a
guard against accidents, not a permission system: use database privileges
for that.

## SSH tunnels

The connection form's **SSH** tab connects through an SSH server (a
bastion). The database host and port are then reached *from the SSH
server*, so you can use names only it can resolve (e.g. `db.internal`).
Lontar opens no local port: every database connection is a forwarded
channel of one SSH connection, made in-process.

- **Authentication:** password, a private key file (`~/.ssh/id_ed25519`
  style paths work; encrypted keys need their passphrase), or the running
  SSH agent (`$SSH_AUTH_SOCK` on Linux/macOS, the OpenSSH agent service on
  Windows). The SSH password and the key passphrase are kept in the OS
  keychain like the database password, each under its own entry, and are
  never shown again ("saved", **Clear saved**).
- **Host keys are always checked.** Lontar reads `~/.ssh/known_hosts` (it
  never writes it) and its own `known_hosts` next to `connections.json`.
  - The first connection to an unknown server shows its key type and
    SHA256 fingerprint. Compare it with what the server's administrator
    gives you, then choose **Trust and connect**. The key is added to
    Lontar's own `known_hosts`.
  - If a server's key **changed**, Lontar refuses to connect and names the
    recorded entry. This can mean someone is intercepting the connection.
    If the change is expected (the server was reinstalled), delete that
    line from the named `known_hosts` file by hand and connect again.
    Lontar never replaces a known key itself.
- A keepalive is sent every 30 seconds. If the SSH connection drops, the
  running query fails with an error, and the next query reconnects the
  tunnel once. Switching databases reuses the tunnel; disconnecting closes it.
- **Test** goes through the tunnel too. Jump hosts (ProxyJump) and Pageant
  are not supported.

Sessions through SSH show an **SSH** badge next to the connection name.

## SSL/TLS

The **SSL** tab sets the TLS mode for PostgreSQL, MySQL and MariaDB (SQLite
has none):

| Mode | Meaning |
|---|---|
| Default | Uses the `sslmode` (PostgreSQL) or `tls` (MySQL/MariaDB) driver option if you set one, otherwise the driver default |
| Disable | No TLS |
| Preferred | MySQL/MariaDB only: TLS if the server offers it, not verified |
| Require | TLS or fail; the certificate is not verified, unless a CA file is set, which then verifies the chain like Verify CA |
| Verify CA | The server certificate must chain to the CA file (or the system roots); the host name is not checked |
| Verify full | Verify CA plus the host name must match the certificate (the connection's host, also through SSH) |

A mode other than Default **wins over** any `sslmode`/`tls` driver option. A
client certificate needs both the certificate and the key file (PEM). Use
**Browse…** or type the paths (`~` is expanded).

## Driver options

The **Advanced** tab (PostgreSQL, MySQL, MariaDB) takes extra driver options
as name/value rows, for example `allowCleartextPasswords` = `true` for MySQL
users that need cleartext authentication ("this user requires clear text
authentication"), or `application_name` for PostgreSQL. Options that have
their own field (host, port, user, password, database, ...) are rejected. Use
cleartext authentication only with TLS or an SSH tunnel.

## Export

**Export…** in the toolbar (also in the command palette) exports the active
tab:

- **Table tab:** every row of the table that matches the current filters,
  in the current sort order. Rows are streamed from the database, so large
  tables are fine.
- **Query result:** the rows already loaded, or **All rows**. All rows
  runs the statement again on a new connection. It is offered only for a
  single read-only statement that returns rows (never a write), runs in a
  read-only transaction, and the statement is shown before it runs.
  Session state from the query tab (temporary tables, `SET`) does not apply
  to it.
- **Selection:** right-click the grid → **Export selection…** writes the
  selected cells as TSV or CSV.

Formats:

- **CSV:** delimiter, header row, quote character, NULL as an empty field,
  `\N` or custom text, LF or CRLF line endings, and an optional UTF-8 BOM
  for Excel. Binary values are hex.
- **JSON:** an array of objects, or NDJSON. Big integers and decimals are
  strings, so they stay exact; "all numbers as strings" is optional. Bytes
  are hex or base64. NULL is `null`.
- **SQL INSERT:** for the connection's dialect, with rows per INSERT and an
  optional `CREATE TABLE` (table exports). Literals are written so that the
  file runs correctly whatever the server settings: PostgreSQL uses `E'…'`
  for strings with backslashes or control characters, and `decode(…,'hex')`
  for bytea. On MySQL/MariaDB, strings that contain a backslash, NUL or
  Ctrl-Z are written as `_utf8mb4 X'…'`, so the file gives the same data
  with and without the `NO_BACKSLASH_ESCAPES` SQL mode. Generated columns
  are left out.

The file is written to a temporary file next to the target and renamed
when complete. Cancelling, or an error, removes the temporary file and
leaves any existing file untouched. Exported files are created readable
only by you (mode 0600 on Linux/macOS).

## CSV import

**Import…** on a table tab loads a CSV file into that table:

1. Choose the file and how to read it: delimiter, quote, header row, a NULL
   marker such as `\N`, empty fields as NULL, and rows to skip. Files must
   be UTF-8; a byte order mark is skipped.
2. Check the preview (the first 50 rows) and the mapping. CSV columns are
   matched to table columns by header name, ignoring case. You can map any
   column to another one, or ignore it. Table columns without a mapping get
   their default.
3. **Import.** Every row is inserted in one transaction, with bound
   parameters and the same type handling as grid edits. Binary columns take
   hex. If any row fails, nothing is imported, and the error names the CSV
   line, and the column when the database says which. Cancelling rolls
   everything back too.

Read-only safe mode does not allow importing, and Confirm mode asks first.

### Switching connections

Press Mod+K, or click the connection name at the top of the sidebar, to
switch to another saved connection without going back to the connection list.
Connections stay open when you switch away: each keeps its tabs, query
results and staged edits, and switching back is instant (no reconnect). The
switcher lists the current connection first, then the other open ones; a
number next to the sidebar name shows how many are open.

A new connection opens before anything changes. If it fails, you stay where
you are and the reason is shown. **Disconnect** in the toolbar closes the
current connection and shows the next open one (or the connection list).
The × next to an open connection in the switcher closes it in the
background, after asking if it has staged edits that were not committed.

- **Editor font size.**
- **Rows per table page** (default 300) and the editor's default **max
  rows** (1,000). Both apply to new tabs.
- **CSV export defaults.**
- **Ask before closing a query tab with unrun changes.**

## Saved connections and passwords

Connections are stored as JSON (schema-versioned, written atomically, file
mode `0600` in a `0700` directory) in the per-user config directory:

| OS | Location |
|---|---|
| Linux | `$XDG_CONFIG_HOME/lontar/connections.json` (default `~/.config/lontar/`) |
| Windows | `%AppData%\lontar\connections.json` |
| macOS | `~/Library/Application Support/lontar/connections.json` |

**Passwords (database, SSH password, SSH key passphrase) are never written to
`connections.json`** and are never sent back to the UI (it only learns whether
one is saved). They are kept in the OS
keychain via [go-keyring](https://github.com/zalando/go-keyring), under the
service `lontar` with the connection ID as the account:

- macOS: Keychain
- Windows: Credential Manager
- Linux: Secret Service (gnome-keyring, KWallet, KeePassXC, ...)

**Linux fallback.** If no Secret Service is reachable (e.g. a minimal window
manager or a headless session), passwords are stored in `secrets.enc` in the
same directory, encrypted with AES-256-GCM. The key lives next to it in
`secrets.key` (mode `0600`). **This is weaker than an OS keychain:** anyone
who can read your files can decrypt it. It only keeps passwords out of
`connections.json` and out of casual view. Start a Secret Service to avoid
the fallback; passwords saved later go to the keychain, and the stale
fallback copy is then removed. On macOS and Windows there is no fallback, and
keychain errors are reported.

Deleting a connection also deletes its saved passwords. `connections.json` is
at schema version 3 (M6). Older files are upgraded on the next save, and a file
from a newer Lontar is refused rather than overwritten.

### Upgrading from dbedit

Lontar was called dbedit. On its first start it moves dbedit's data over:

- **Config directory.** `dbedit/` in the per-user config directory (with
  `connections.json`, `history.db`, `settings.json`, `known_hosts` and the
  Linux fallback `secrets.enc`/`secrets.key`) is renamed to `lontar/`. If
  that fails (e.g. it would cross file systems) it is copied, keeping the
  file permissions, and the old directory is removed only after the copy
  succeeded. Nothing is moved when `lontar/` already exists; the old
  directory is then left alone and a line is logged. If the move fails,
  Lontar uses `dbedit/` for that run and tries again on the next start.
- **Passwords in the OS keychain** move from the service `dbedit` to
  `lontar` the first time each one is needed. Saving or deleting a password
  also removes any copy left under `dbedit`. On macOS the keychain may ask
  once whether Lontar may read an item that dbedit created.
- **Unsent query drafts** are not carried over in the desktop app. The
  webview keeps its local storage under the program name
  (`~/.local/share/dbedit` on Linux, `%AppData%\dbedit.exe` on Windows, the
  `dev.dbedit.app` WebKit data on macOS), so Lontar starts with an empty
  one. (`dbedit.*` keys are moved to `lontar.*` where the storage is shared,
  e.g. server mode in a browser.) The old webview directories can be deleted
  by hand.

On Windows, uninstall dbedit before or after installing Lontar: the two are
separate entries in "Apps & features". Uninstalling dbedit keeps the data
that Lontar has already moved.

## Installing

Download the file for your OS from the project's GitHub Releases page. Check
it against `SHA256SUMS` from the same release (`sha256sum -c SHA256SUMS
--ignore-missing` on Linux, `shasum -a 256 -c SHA256SUMS --ignore-missing` on
macOS, `Get-FileHash` on Windows).

| OS | File | Notes |
|---|---|---|
| Linux (Debian 13+, Ubuntu 24.04+) | `lontar-<version>-linux-amd64.deb` | `sudo apt install ./lontar-*.deb` pulls in GTK4 (`libgtk-4-1`) and WebKitGTK 6.0 (`libwebkitgtk-6.0-4`). |
| Linux (Fedora 39+) | `lontar-<version>-linux-x86_64.rpm` | `sudo dnf install ./lontar-*.rpm` pulls in `gtk4` and `webkitgtk6.0`. |
| Linux (any, x86_64) | `lontar-<version>-linux-x86_64.AppImage` | `chmod +x lontar-*.AppImage && ./lontar-*.AppImage`. Self-contained (GTK and WebKitGTK bundled), so it is large (~130 MB). |
| Windows 10/11 (x64) | `lontar-<version>-windows-amd64-setup.exe` | Per-user installer, see below. |
| Windows (portable) | `lontar-<version>-windows-amd64-portable.zip` | Just `lontar.exe`; needs the WebView2 runtime (built into Windows 11). |
| macOS 12+ (Apple silicon and Intel) | `lontar-<version>-macos-universal.dmg` | Open it and drag Lontar to Applications. |

The packages install `lontar` to `/usr/bin`, a desktop entry
(`Development;Database;`) and the icon in the `hicolor` theme. The optional
`gnome-keyring` recommendation provides the Secret Service; without one,
Lontar stores passwords in its encrypted file instead (see "Saved connections
and passwords").

**Windows installer.** It installs **per user** into
`%LOCALAPPDATA%\Programs\Lontar` (no administrator prompt), adds a Start-menu
and a desktop shortcut and an "Apps & features" entry with an uninstaller.
If the Microsoft Edge WebView2 runtime is missing it runs Microsoft's
Evergreen bootstrapper, which downloads the runtime (**internet access
needed** for that step only; Windows 11 and current Windows 10 already have
it). Uninstalling removes the program and the WebView2 cache
(`%AppData%\lontar.exe`) but keeps your connections, history and settings in
`%AppData%\lontar` and the passwords in Credential Manager.

**Unsigned builds.** Releases are only code-signed when the maintainers'
signing secrets are configured (see "Releasing"). Unsigned builds work, but
the OS warns first:

- **Windows:** SmartScreen shows "Windows protected your PC". Click
  **More info → Run anyway**.
- **macOS:** Gatekeeper says the app "cannot be opened because the developer
  cannot be verified" (or that it is "damaged"). Either right-click (Control-
  click) Lontar in Applications, choose **Open** and confirm **Open**
  (on macOS 15+: try to open it once, then **System Settings → Privacy &
  Security → Open Anyway**), or remove the quarantine flag:
  `xattr -dr com.apple.quarantine /Applications/lontar.app`.
- **Linux:** packages are not GPG-signed; verify them with `SHA256SUMS`.

### Versioning

Every build and package task stamps the same version (`VERSION` in the root
`Taskfile.yml`) into the Go binary (`-ldflags -X
lontar/internal/services.Version=…`, shown in the status bar), the macOS
`Info.plist`, the Windows VERSIONINFO resource and installer, and the
`.deb`/`.rpm` metadata. It comes from:

1. `LONTAR_VERSION` if set (a leading `v` is dropped), e.g.
   `LONTAR_VERSION=v26.11.1 wails3 task package:linux`; otherwise
2. `git describe --tags --always --dirty`: tag `v26.11.1` → `26.11.1`,
   `v26.11.1-4-gabc1234` → `26.11.1-4-gabc1234`, an untagged commit →
   `0.0.0-dev+<hash>[-dirty]`; otherwise
3. `0.0.0-dev` (no git), which is also the default of a plain `go build`.

Fields that only take numbers (`CFBundleVersion`, Windows file version, NSIS)
get the `X.Y.Z` core. `build/config.yml`'s `version` is only a baseline.

### Building packages

Packages are built natively on each OS (the release workflow does this on
GitHub's runners). Output goes to `bin/`.

| Task | Host | Output | Extra tools |
|---|---|---|---|
| `wails3 task package:linux` | Linux | `lontar-x86_64.AppImage`, `lontar.deb`, `lontar.rpm`, `lontar.pkg.tar.zst` | none: nfpm is built into `wails3`; the AppImage step downloads linuxdeploy (internet). |
| `wails3 task package:windows` | Windows (or Linux with `GOOS=windows`) | `lontar-amd64-installer.exe` | [NSIS](https://nsis.sourceforge.io) `makensis` on `PATH`; the WebView2 bootstrapper is downloaded. `INSTALL_SCOPE=machine` builds a per-machine (Program Files, UAC) installer instead. |
| `wails3 task package:darwin` | macOS | universal `lontar.app` + `lontar.dmg` | Xcode command line tools. The app is ad-hoc signed only. |

`GOOS=windows wails3 build` cross-compiles `bin/lontar.exe` (with icon,
manifest and version resource) from Linux or macOS, since the Windows build
needs no cgo. The macOS and Linux GUI builds need cgo and so their own OS (or
the `wails3 task setup:docker` cross-compile image).

Identity (name, publisher `Lontar contributors`, bundle id `dev.lontar.app`,
description, copyright) is set in `build/config.yml`. After changing it run
`wails3 task common:update:build-assets`, then re-apply what that command
overwrites from the Wails templates: `build/linux/nfpm/nfpm.yaml` (Lontar's
dependencies, icons, `Apache-2.0` license and the LICENSE/NOTICE files) and the hand-added keys in
`build/darwin/Info*.plist` (the comment block, `LSApplicationCategoryType`,
`LSMinimumSystemVersion` 12.0, the boolean `NSHighResolutionCapable`, and
`CFBundleDisplayName` "Lontar"); restore `build/darwin/entitlements.plist`,
which it deletes; delete the `build/ios` and `build/linux/desktop` files it
recreates (unused). `build/linux/lontar.desktop` is maintained by hand.

### Regenerating the icon

`build/appicon.svg` is the only source of the icon. After editing it run:

```sh
wails3 task icons:render
```

This renders it with `tools/iconrender` (pure Go, `oksvg`; keep to paths,
basic shapes and gradients) into `build/appicon.png` (1024²), the Linux
`hicolor` PNGs (16–512) and scalable SVG, the favicon
(`frontend/public/favicon.svg`) and the dmg icon/background, then rebuilds
`build/windows/icon.ico` and `build/darwin/icons.icns` with `wails3 generate
icons`. Commit the results; builds do not re-render.

## Releasing

Releases use calendar versioning: **`vYY.MM.MICRO`**, with the two-digit
year, the month without a leading zero, and a counter that restarts at 1 every
month (`v26.11.1`, `v26.11.2`, `v26.12.1`). A pre-release adds a suffix,
`v26.11.3-rc.1`; it does not use up its number, so `v26.11.3` follows it.
`tools/calver` checks the format; tags in any other format fail the release.

1. Make sure CI is green on `main`.
2. Tag and push the next version:
   ```sh
   git fetch --tags
   wails3 task release:next          # e.g. 26.11.2
   git tag v26.11.2 && git push origin v26.11.2
   ```
3. `.github/workflows/release.yml` checks the version, runs the short tests
   on Linux, Windows and macOS, builds every package stamped with `26.11.2`,
   signs what it has secrets for, and creates a **draft** GitHub Release with
   the files and `SHA256SUMS` (versions with a `-` are marked pre-release).
4. Review the draft and publish it.

The workflow can also be started by hand (**Actions → Release → Run
workflow**). If you leave the version empty, it uses the next number for the
current month (UTC), based on the existing tags and releases. You can also
enter a version such as `26.11.2-rc.1`. The draft targets the dispatched
commit, with tag `v<version>`. The run fails if that tag or a release (even a
draft) for it already exists, so publish or delete a draft before starting
another run. `wails3 task release:checksums DIR=dist` writes the same
`SHA256SUMS` locally.

Signing is optional; each step is skipped when its secrets are missing:

| Secret | Used for |
|---|---|
| `WINDOWS_CERT_PFX` | Base64 of the Authenticode code-signing certificate (`.pfx`) |
| `WINDOWS_CERT_PASSWORD` | Its password |
| `MACOS_CERT_P12` | Base64 of the "Developer ID Application" certificate + key (`.p12`) |
| `MACOS_CERT_PASSWORD` | Its password |
| `APPLE_ID` | Apple ID used for notarization |
| `APPLE_TEAM_ID` | The Apple Developer team ID |
| `APPLE_APP_PASSWORD` | An app-specific password for that Apple ID |

Windows signs `lontar.exe` before it goes into the installer, then the
installer (`build/windows/sign.ps1`, signtool, SHA-256 + RFC 3161 timestamp).
macOS signs the app with the hardened runtime and
`build/darwin/entitlements.plist` (only `com.apple.security.network.client`,
Wails' production preset), then signs, notarizes (`notarytool`) and staples
the dmg (`build/darwin/sign-notarize.sh`). With the certificate but no Apple
ID secrets the dmg is signed but not notarized.

Setting up the macOS secrets (Apple Developer account):

1. In Xcode → Settings → Accounts → Manage Certificates (or on
   developer.apple.com → Certificates) create a **Developer ID Application**
   certificate. Note that this is not "Apple Development" or "Mac App
   Distribution".
2. In Keychain Access, export that certificate *with its private key* as a
   `.p12` file, using a password. Store
   `base64 -i DeveloperID.p12 | pbcopy` as `MACOS_CERT_P12` and the password
   as `MACOS_CERT_PASSWORD`.
3. On account.apple.com → Sign-In and Security → App-Specific Passwords,
   create a password for `APPLE_APP_PASSWORD`. `APPLE_ID` is the account's
   e-mail, and `APPLE_TEAM_ID` is the 10-character Team ID shown on
   developer.apple.com → Membership.
4. Add all five under **Settings → Secrets and variables → Actions** of the
   GitHub repository. The `.app` targets macOS 12
(`LSMinimumSystemVersion`, matching `-mmacosx-version-min=12.0`).
